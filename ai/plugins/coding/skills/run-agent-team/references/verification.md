# Verification and activation

Static bundle/graph/Git checks establish resource closure and the stated contract,
not actual role selection, model use, parallel execution or containment.
Record those limits. Use representative requests, non-triggers and held-out cases
in the existing create-skill evaluation schema, retaining observed evidence and
unknown telemetry. Never report a fixture's expected result as a live result.

## Disposable two-worker native smoke

Only after scoped authorization for model use, disposable worktree setup, checks,
fixture story commits and archival:
1. Verify activated skill/role discovery in a fresh task in the selected harness. Preflight exact
   worker/model controls and required story-reviewer selection, same-session review
   follow-up, current main session, model evidence/unknowns and capacity. No global
   changes during the smoke.
2. Use a project-local disposable Git repository with clean prepared integration
   and two task branches, an approved checklist plan, two independent substantial
   file-format adapters with focused tests, and a dependent integration story.
3. Use the current main session to dispatch two workers directly through supported
   native controls, with preferred models or recorded fallbacks under
   runtime-selection.md, without reading or invoking multi-agent-coordinator.
   Record returned role/session IDs, selection evidence,
   bases, paths/private outputs and actual start/finish events. Dispatch both
   before waiting; separately require observed active overlap to pass this smoke.
   No artificial sleep or invented timestamps to manufacture evidence.
4. Integrate each result through the existing checks/review/authorized commit gates.
   Confirm the dependent task starts only from a clean base containing both
   verified integration delivery commits. Keep writer ownership disjoint.
5. Verify task completion, quiescent writers and the required archive/receipt.
   Report exact check results, any failures, requested versus observed model data,
   review sessions and remaining activation gaps. Preserve artifacts if blocked.

## Sustained coordination evaluation

The two-worker smoke establishes initial dispatch/overlap only. Evaluate sustained
useful concurrency and verified delivery over more ready stories than worker slots,
including repeated handoff, check-yield, remediation, review and commit events.
Use the existing evaluation fixtures and authorized recorded transcripts or a
separately authorized disposable run; never interact with an existing team merely
to validate source instructions. No artificial delays or application-plan execution
under a source-edit grant.

| Scenario | Expected decision and evidence |
| --- | --- |
| Slow SDK check yields while independent work is ready | Reassess and dispatch before the next wait if capacity, resources and queue permit; retain one check handle/result and the candidate freeze. |
| Handoff needs substantial source repair | Send bounded repair to the original worker when feasible; record exclusive ownership transfers in both directions, actual rechecks and unchanged budgets. A small integration fix may stay with the main thread. |
| Shared build hooks block worker compilation | Report early, run feasible checks, label the source-only handoff unqualified and arrange a minimal integration compile checkpoint. No broad build duplication or invented pass. |
| Integration queue reaches its limit | Stop new-story admission, drain through qualification/remediation/delivery, preserve incoming active-worker results and reviewer capacity. Resume admission only when eligible. |
| Idle/completed/pending-init capacity is uncertain | Inspect supported state and documented semantics, distinguish occupancy from unknowns and record exactly which admission is affected; continue safely eligible work. |
| Initial review finished but targeted continuation may be needed | Retain the required reviewer session; no close/respawn to gain worker capacity or another pass. |
| Dependency or exclusive SDK/output resource prevents concurrency | Serialize only the constrained work, document the reason and do not release dependencies before verified integration commit. |

Inspect the ordered events and artifacts across multiple delivery cycles, not just
maximum occupied slots: did every yield/refill decision respect ownership, queue,
resources and budgets; did candidates get qualified and committed; were dependencies
released on verified delivery? Record actual check commands/results, session mapping,
queue changes and concrete idle/serialization reasons without a second registry.
Use observed timestamps only when supplied. Do not infer performance gains from
dispatch count, expected fixture outcomes, static text or a hypothetical timeline.
Keep held-out combined scenarios for later authorized evaluation; label a manual
source walkthrough as static instruction validation, never observed runtime behavior.

Test unavailable worker/reviewer controls, unavailable preferred model controls,
unknown main-session telemetry, fixed reviewer pins, explicit user model
constraints, unclear ownership, stale bases, capacity pressure, uncertain spawn, review blockers and
archival failures with controlled fixtures/recorded transcripts. The main thread
retains dispatch, Git, merging and trackers throughout. Keep exact native review
where required. Do not perform unapproved live retries or claim a custom role was
invoked from an ordinary worker's label. Unknown main model plus a Luna-pinned
native story-reviewer should proceed when the other gates pass and no explicit
user model constraint conflicts. A missing exact reviewer or an unsatisfied
explicit model requirement must still block the affected path. Preserve a valid
passing review and pending commit when reconciling a model-policy-only stall;
do not consume another review pass merely because the preference policy changed.

## Activation boundary

Source delivery does not activate installed skills, roles or configuration. Under
separate installation authorization, preserve customized copies and coordinate
the coding plugin and any separately requested role/runtime changes. Restart and
verify unique discovery in a fresh task. Respect installed worker/reviewer pins;
changing them is unnecessary for preference fallback. No cache deletion or
automatic installation.
A runtime lacking required native specialist/reviewer selection cannot prove their
invocation; no custom coordinator capability is needed. Missing required gates
block this smoke rather than permit a generic substitute. Check the actual runtime
on every execution attempt.

Verify takeover from an older run waits for its quiescent dispatcher and reconciles
every live worker/reviewer ID and consumed pass. No proxy-spawning or competing
dispatch loops.
